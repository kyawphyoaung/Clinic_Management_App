
# Phase 707 – Additional Refinements

## Overview
This document outlines remaining refinements for the Phase 707 implementation. All changes follow the specifications exactly as described.

---

## 1. Partner Set Password Page (`/partner/set-password`)

### Issue
- After submitting a new password, the page does not show a success message.
- The user is redirected immediately without confirmation.

### Requirement
- After password is updated, show an alert: **"Password Updated Successfully"**
- Display a countdown: **"Redirecting to Partner Login Page (5, 4, 3, 2, 1...)"**
- After the countdown finishes, redirect to `/partner/login`.

---

## 2. Requested Deposit System

### 2.1 Remove "Mark Sent" Logic
- Remove all "Mark Sent" buttons and related logic from Requested Deposit.
- When a Requested Deposit is created, it is immediately recorded as requested.

### 2.2 Exchange Rate & Currency Logic
- The **Exchange Rate** field should only appear **after** a Currency is selected.
- **Default Currency:** The patient's country currency (from their registered country).
- When the user enters an Amount:
  - The system calculates the equivalent amount in the selected currency using the exchange rate.
  - Display the converted amount next to the original amount.

### 2.3 Requested Deposit Table (Admin Dashboard)
- **Statuses (2 only):**
  1. **Awaiting Deposit** (Red)
  2. **Deposit Received** (Green)
- **Columns:** `Requested At | Amount | Status`
- **Amount Color:**
  - `Awaiting Deposit` → Red
  - `Deposit Received` → Green
- **Actions:**
  - Clicking a row allows **Update** and **Delete**.
  - **Delete is only allowed** if `Status = Awaiting Deposit`.
  - If `Status = Deposit Received`, Delete is **disabled**.

### 2.4 Agent Dashboard – Requested Deposit Table
- Display a table: **Patient's Requested Deposit Amount**.
- Shows which patients have a requested deposit and the amount.

### 2.5 Deposit Billing Table (Patient Detail Page)
- **Columns:** `Date | Amount | Method | Reference | Notes | Recorded By`
- **Amount Color:** Orange/Gold.
- **Actions:** Each row can be **Updated** or **Deleted**.
- **Restriction:** If the deposit has already been applied to treatment charges (used in payment), **Update and Delete are NOT allowed**.

## 3. Visits Table (Patient Detail Page)

### 3.1 Edit Visit
- When editing a visit, allow the user to modify:
  - Agent connection (change the linked agent).
  - Linked Treatments (add/remove treatments).

### 3.2 Delete Visit
- Show an **Alert** before deletion.
- The alert must display:
  - All linked Treatments.
  - All linked Charges and Payments under those treatments.
- This gives the user full visibility of what will be affected.

### 3.3 Visit ID
- Rename "Display ID" to **"Visit ID"** in the Visits table.

### 3.4 Visit ↔ Appointment Link
- Each Visit record should also link to the associated Appointment (if one exists).

---

## 4. Treatments Table (Patient Detail Page)

### Requirement
- Add a **Treatment ID** column to the Treatments table.

---

## 5. Treatment Detail Page – Charges Table

### Issue
- Currently, clicking a charge row only allows viewing the detail.
- Update and Delete are not available.

### Requirement
- Each charge row must have:
  - **View** (existing)
  - **Update** (edit the charge)
  - **Delete** (remove the charge)
- **Restriction:** Update and Delete are **only allowed** if `Paid = No`.
- If `Paid = Yes`, Update and Delete are **disabled**.

---

## 6. Treatment Detail Page – Payments Table (Strike-Through Logic)

### Context
- Charges total: NT$6000 (3 charges, each NT$2000).
- Payment 1: NT$2000 → Remaining Balance = NT$4000
- Payment 2: NT$2000 → Remaining Balance = NT$2000
- Payment 3: NT$2000 → Remaining Balance = NT$0

### Requirement
- The **Remaining Balance** column shows the balance after each payment.
- **Strike-Through Rule:**
  - Only the **Remaining Balance value** is struck through.
  - NOT the entire row.
  - Only for rows where the remaining balance has been fully cleared by a later payment.
- **Example:**
  - Payment 1 (Remaining Balance: NT$4000) → **NO** strike-through.
  - Payment 2 (Remaining Balance: NT$2000) → **NO** strike-through.
  - Payment 3 (Remaining Balance: NT$0) → **NO** strike-through (final payment).
  - Earlier rows (Payment 1 and 2) will have their remaining balance struck through **only after the final payment clears the balance**.
